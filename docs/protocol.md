# Протокол Книгописи

У Книгописи нет своего HTTP API. Все записи — события [Nostr](https://github.com/nostr-protocol/nips)
(NIP-01), и relay на узлах — это и есть API. Читать может кто угодно без входа, писать — любой, кто подписывает
события своим ключом. Документ для авторов сторонних клиентов: приложений, ботов, экспорта.

Описано то, что делает сайт. Если документ и код разошлись, прав код: `src/lib/records.ts`, `profiles.ts`,
`follows.ts`, `importer.ts`, политика записи — `relay/write-policy.py`.

## Узлы

- Главный — `wss://www.knigopis.com`. Все известные — в [`src/known-relays.json`](../src/known-relays.json).
- Узлы синхронизируются между собой, но сайт пишет сразу на все известные (успех — если принял хоть один),
  а читает со всех и объединяет ответы. Клиенту стоит делать так же.
- Описание узла (NIP-11): `curl -H 'Accept: application/nostr+json' https://www.knigopis.com/`.

## Ключ и вход

Аккаунт — пара ключей Nostr (secp256k1). Логина и пароля нет, сервер о пользователе ничего не хранит.

Сайт держит ключ в браузере как `nsec1…` (NIP-19) и умеет отдать его двумя способами:

- **ссылка входа** `https://www.knigopis.com/login#nsec1…` (часть после `#` на сервер не уходит);
- **файл резервной копии** — текст, где среди пояснений есть `nsec1…`.

Сайт принимает `nsec1…`, 64 hex-символа или весь текст копии (ищет в нём `nsec1…`). Приложению стоит
понимать то же самое.

Ещё лучше, если приложение ключа не видит вовсе: подписывать события можно через NIP-55 (подписыватель
на Android, например Amber) или NIP-46 (удалённый подписыватель). Сам сайт их пока не поддерживает.

Адреса на сайте:

- `/u/<первые 16 hex-символов ключа>` или `/u/npub1…` — страница пользователя;
- `/archive/<старый userId>` — его страница в архиве.

## События

| kind | что | NIP | хранится |
|---|---|---|---|
| 0 | профиль | 01 | последняя версия на автора |
| 3 | подписки | 02 | последняя версия на автора |
| 5 | запрос удаления | 09 | — |
| 10002 | список relay | 65 | relay принимает, сайт пока не публикует |
| 31110 | прочитанная книга | — | последняя версия на (автор, `d`) |
| 31111 | «хочу прочитать» | — | последняя версия на (автор, `d`) |
| 31112 | заявка на старый аккаунт | — | последняя версия на (автор, `d`) |

31110–31112 — адресуемые события (диапазон 30000–39999). Номера свободны в реестре NIPs на 2026-10.

### 31110 — прочитанная книга

```json
{
  "kind": 31110,
  "content": "Заметки о книге",
  "tags": [
    ["d", "QbQItEDCRDjt"],
    ["title", "Князь Серебряный"],
    ["author", "Алексей Толстой"],
    ["read", "2026-11-05"],
    ["alt", "Прочитанная книга: «Князь Серебряный» — Алексей Толстой"]
  ]
}
```

| тег | | |
|---|---|---|
| `d` | обязателен | id записи, уникальный у автора. Сайт делает 12 символов `[A-Za-z0-9]`, у перенесённых — старый id |
| `title` | обязателен | непустой |
| `author` | если есть | |
| `read` | если есть | дата прочтения: `ГГГГ`, `ГГГГ-ММ` или `ГГГГ-ММ-ДД`. Нет тега — дата неизвестна |
| `legacy` | у перенесённых | `["legacy", <старый userId>, <старый id записи>, <старый createdAt "ГГГГ-ММ-ДД ЧЧ:ММ:СС" или "">]`. При правке сохраняется |
| `alt` | желательно | NIP-31: описание для клиентов, которые не знают этот kind |

`content` — заметки, простой текст. Переводы строк значимы, разметки нет.

### 31111 — «хочу прочитать»

То же, что у книги, только без `read` и с одним новым тегом:

- `priority` — целое число строкой, чем больше, тем важнее (в старых данных 0–100). Сайт его не редактирует,
  но при правке сохраняет.

`alt`: `Хочу прочитать: «<title>» — <author>`.

**Желания публичны.** Сайт показывает их только владельцу, но события не шифруются — как и в старом
хранилище, их может прочитать любой.

### 31112 — заявка на старый аккаунт

```json
{
  "kind": 31112,
  "content": "",
  "tags": [
    ["d", "83820536-yandex"],
    ["nickname", "lucius"],
    ["alt", "Перенос записей «lucius» из архива старой Книгописи"]
  ]
}
```

Смысл заявки: «этот ключ перенёс к себе записи старого аккаунта `d`». Старый userId выглядит как
`<uid>-<провайдер>` (`83820536-yandex`), у аккаунтов с паролем — `<логин>-local`, и логин бывает email.

Проверить заявку нельзя: старый вход мёртв, подать её может кто угодно, и заявок на один id бывает
несколько. Сайт показывает их все.

### 0 — профиль

`content` — JSON. Сайт пишет `name` и `display_name` (одинаковые) и не трогает чужие поля.
Тег `["u", <первые 16 hex-символов ключа>]` нужен для коротких ссылок `/u/…`: relay не ищут по началу ключа.

Как править: взять последнюю версию с relay, поменять поля, поставить `created_at` строго больше прежнего.
При равном `created_at` relay оставит версию с меньшим id, и правка может пропасть.

### 3 — подписки

Стандарт NIP-02: теги `["p", <pubkey>]`, `content` сохранять как есть. Менять, отталкиваясь от последней
версии с relay, а не от локального кеша, — иначе затрёте подписки, сделанные с другого устройства.

## Правила

### Правка

Правка — новое событие с тем же `d` и `created_at` строго больше прежнего: при равном времени relay оставит
версию с меньшим id и отклонит новую («replaced: have newer event»). Из нескольких версий одного адреса
`(kind, pubkey, d)` клиент берёт последнюю, при равном времени — с меньшим id. Узлы могут отдать
несколько версий, так что сворачивать их надо всегда.

### Удаление

Удаление делается в два шага, оба — с `created_at` строго больше, чем у удаляемой версии:

1. **Надгробие** — то же `kind` и `d`, без названия:
   `{"kind": 31110, "content": "", "tags": [["d", "<d>"], ["deleted", "1"]]}`.
2. **Запрос NIP-09:** `{"kind": 5, "content": "", "tags": [["a", "31110:<pubkey>:<d>"], ["k", "31110"]]}`.

Наши узлы (strfry) по запросу убирают все версии, и записи не остаётся вовсе. Relay без NIP-09 оставят
надгробие. Поэтому клиент обязан скрывать записи с тегом `deleted`.

Гарантированно стереть запись с чужих relay и из копий нельзя.

### Перенос из архива

Сайт переносит записи так:

1. Публикует заявку 31112.
2. Публикует книги и желания с `d` = старым id записи и тегом `legacy`. Повторный перенос не плодит дубли,
   уже перенесённое пропускается.
3. `created_at` ставит текущее время, у каждого события — своя секунда подряд. Иначе постраничное чтение
   по `until` теряет события. Старую дату в `created_at` не ставить: relay не примет событие старше трёх лет.
   Исходная дата хранится в `legacy`.
4. Старые подписки: ищет заявки по `#d` = старым id и подписывается на их ключи (kind 3). Тех, кто ещё
   не перенёсся, никуда не записывает — заново находит по своим заявкам и архиву.

### Лента

Главная показывает последние книги без тега `legacy`, иначе перенос сотен книг забил бы ленту.

## Запросы

| что | фильтр |
|---|---|
| книги пользователя | `{"kinds":[31110],"authors":["<pk>"]}` |
| его желания | `{"kinds":[31111],"authors":["<pk>"]}` |
| одна запись | `{"kinds":[31110],"authors":["<pk>"],"#d":["<d>"]}` |
| лента | `{"kinds":[31110],"limit":300}`, затем убрать надгробия и `legacy` |
| профили | `{"kinds":[0],"authors":["<pk>", …]}` (сайт шлёт по 200 ключей) |
| ключ по короткой ссылке | `{"kinds":[0],"#u":["<16 hex>"]}`, затем оставить ключи, которые правда так начинаются |
| подписки | `{"kinds":[3],"authors":["<pk>"]}` → теги `p` |
| кто подписан на него | `{"kinds":[3],"#p":["<pk>"]}` |
| кто перенёс старый аккаунт | `{"kinds":[31112],"#d":["83820536-yandex"]}` |
| что перенёс этот ключ | `{"kinds":[31112],"authors":["<pk>"]}` |

- **Постранично:** relay отдаёт не больше `limit` (максимум 5000). Если событий пришло ровно столько, повторите
  запрос с `until` = самый старый `created_at`, повторы отсейте по id.
- **Поиск по названию и автору** relay не умеет: индексируются только однобуквенные теги (`d`, `p`, `u`, `a`…).
  Ищите среди скачанных событий или по архиву (`books-index.json`).

## Что примет relay

Политика записи узлов (`relay/write-policy.py`, настройки strfry — `relay/strfry.conf`):

- **kind:** 0, 3, 5, 10002, 31110–31112. Остальные — `blocked:`.
- **Теги:** у 31110–31112 нужен `d`; у 31110 и 31111 — непустой `title` (кроме надгробий).
- **Размер:**
  - `content` — профиль до 4000 символов, книга и желание до 20 000, остальное до 2000;
  - событие целиком — до 64 КБ, значение тега — до 1024 байт.
- **Время:** `created_at` не старше трёх лет и не дальше 15 минут в будущее.
- **Частота:** 3000 событий сразу, дальше +2 в секунду на IP-адрес (у IPv6 — на сеть /64). Ответ
  `rate-limited:` — повторить позже.
- **Место:** когда на узле кончается диск, любая запись получает `blocked:`.

Причина отказа приходит в ответе `OK` (NIP-01), текстом по-русски, например
`invalid: у книги нет названия`.

## Архив старой Книгописи (HTTP, только чтение)

Снимок старого хранилища (repo2) на 2026-10-30 — статические файлы на каждом узле. Обновляться они не будут.

- **`/legacy/index.json`:** `{builtAt, source, commit, users: [[id, ник, книг, желаний, "ГГГГ-ММ-ДД"], …]}`.
- **`/legacy/users/<id>.json`:**
  `{id, nickname, lang, createdAt, updatedAt, subscriptions: [старые id], books: […], wishes: […]}`.
  - Книга: `id, title, author, readYear, readMonth, readDay, notes, createdAt, updatedAt`.
  - Желание: `id, title, author, priority, notes, createdAt, updatedAt`.
  - Даты — строки `"ГГГГ-ММ-ДД ЧЧ:ММ:СС"` или `null`.
  - id в адресе кодируйте (`encodeURIComponent`): у аккаунтов с паролем это бывает email.
- **`/legacy/books-index.json`:** `[[название, автор, номер пользователя в index.users], …]`.
- **`/legacy/latest.json`:** `{users, books, items: […]}` — последние книги с заметками, по одной на человека.

Если файла нет, узел отвечает 404. Заголовков CORS нет: из чужой веб-страницы `fetch` не сработает,
из приложения — без ограничений.

## Соответствие старому API

Если клиент работал со старым `api.knigopis.com`:

| старый API | теперь |
|---|---|
| `GET /user/get-credentials`, `/auth/login` | своего входа нет: ключ из ссылки или копии, либо NIP-55/NIP-46 |
| `GET /users/current` | свой профиль: kind 0 со своим ключом |
| `GET /users/:id`, `PUT /users/:id` | kind 0 |
| `GET /books`, `GET /users/:id/books` | kind 31110 по `authors` |
| `POST /books`, `PUT /books/:id` | kind 31110 с новым или тем же `d` |
| `DELETE /books/:id` | надгробие + kind 5 |
| `/wishes…` | то же с kind 31111 |
| `GET /subscriptions`, `POST`/`DELETE /subscriptions/:id` | kind 3 |
| `GET /books/latest-notes` | лента: kind 31110 с `limit`, без `legacy`, с непустым `content` |
| старый userId → новый ключ | заявки kind 31112 по `#d` |
| данные до переезда | `/legacy/users/<id>.json` |

## Пример (JavaScript, nostr-tools)

```js
import { SimplePool } from 'nostr-tools/pool';
import { finalizeEvent } from 'nostr-tools/pure';

const relays = ['wss://www.knigopis.com'];
const pool = new SimplePool();

// Книги пользователя: последняя версия каждой, без надгробий.
const events = await pool.querySync(relays, { kinds: [31110], authors: [pubkey], limit: 5000 });
const latest = new Map();
for (const ev of events) {
  const d = ev.tags.find((t) => t[0] === 'd')?.[1] ?? '';
  const cur = latest.get(d);
  if (!cur || ev.created_at > cur.created_at || (ev.created_at === cur.created_at && ev.id < cur.id)) {
    latest.set(d, ev);
  }
}
const books = [...latest.values()].filter((ev) => !ev.tags.some((t) => t[0] === 'deleted'));

// Новая книга.
const ev = finalizeEvent(
  {
    kind: 31110,
    created_at: Math.floor(Date.now() / 1000),
    content: 'Заметки',
    tags: [
      ['d', 'QbQItEDCRDjt'],
      ['title', 'Князь Серебряный'],
      ['author', 'Алексей Толстой'],
      ['read', '2026-11-05'],
      ['alt', 'Прочитанная книга: «Князь Серебряный» — Алексей Толстой'],
    ],
  },
  secretKey,
);
await Promise.any(pool.publish(relays, ev));
```

На других языках подойдёт любая библиотека Nostr с NIP-01: например, rust-nostr (есть привязки для Kotlin
и Swift) или Quartz из Amethyst для Android.
