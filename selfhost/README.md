# Узел Книгописи

Узел — это сайт (статика вместе с архивом старой Книгописи) и relay (strfry), где хранятся записи.
Все узлы одинаковые и синхронизируются друг с другом, а клиент пишет сразу на несколько.
Поэтому исчезновение одного узла ничего не ломает. Подделать запись узел не может: каждая подписана ключом автора.

## Что нужно

- **Сервер:** Linux x86_64 с Docker и Compose v2. Хватит 512 МБ памяти (relay занимает десятки мегабайт) и ~1 ГБ диска.
- **Домен или поддомен** с A-записью на сервер.

Готовый образ relay — только под amd64. На ARM (Raspberry Pi и т. п.) соберите сами: `docker compose build relay`.
Это компиляция strfry, 10–30 минут.

## Вариант 1. Чистый сервер — всё в Docker, HTTPS сам

```sh
git clone https://github.com/gurov/knigopis-p2p.git /opt/knigopis
cd /opt/knigopis/selfhost
cp .env.example .env      # DOMAIN, UPSTREAM — см. комментарии в файле
./update.sh               # скачает сайт и образ relay из последнего релиза и запустит
```

Порты 80 и 443 должны быть свободны: сертификат Caddy получит сам. Откройте `https://<DOMAIN>`.

## Вариант 2. На сервере уже есть nginx или Caddy

1. В `.env` удалите строку `COMPOSE_PROFILES=web`.
2. Запустите `./update.sh`. Он поднимет только relay на `127.0.0.1:7777` и положит сайт в `selfhost/site`.
3. Настройте свой веб-сервер. На одном домене WebSocket и NIP-11 уходят на relay, остальное — статика с запасным `index.html`.
   - **nginx:** `nginx.conf.example`;
   - **Caddy:** `Caddyfile` из этого каталога — замените `relay:7777` на `127.0.0.1:7777`, а `/srv` на путь к `site`.
     Рабочий пример — `deploy/knigopis.caddy` (так устроен knigopis.bizibah.com).

## Вариант 3. Только зеркало сайта

Возьмите `knigopis-site.tar.gz` из релиза и выложите на любой статический хостинг: GitHub Pages, Netlify, свой nginx.
Для хостингов без SPA-маршрутов есть `404.html`. Своего relay у зеркала нет — оно работает с известными узлами.

## Как стать репликой

1. **Поднимите узел** (вариант 1 или 2). В `UPSTREAM` в `.env` перечислите через пробел все узлы
   из `src/known-relays.json`. Первая синхронизация заберёт всю историю, это минуты. Дальше узлы обмениваются
   записями в обе стороны раз в `SYNC_INTERVAL` секунд.

   Синхронизация двусторонняя, поэтому на остальных узлах ничего менять не нужно: новый узел сам связывается
   со всеми прежними. Получается сетка без центра, и если пропадёт любой узел, остальные продолжат обмениваться
   записями. Если в `UPSTREAM` только один узел, вся синхронизация вашего узла держится на нём.
2. **Проверьте:**
   ```sh
   curl -H 'Accept: application/nostr+json' https://<DOMAIN>   # описание relay
   docker compose logs relay | grep Writer                      # идёт ли синхронизация
   ```
3. **Пришлите PR** с адресом `wss://<DOMAIN>` в `src/known-relays.json`. Со следующего релиза все клиенты будут
   записывать и на ваш узел.

До этого ваш узел можно добавить вручную: «Настройки → Серверы».

## Главный узел и переезд

Главный узел — тот, на чей адрес заходят читатели (сейчас knigopis.bizibah.com, потом knigopis.com).
Для синхронизации он такой же, как остальные.

Ключ читателя хранится в браузере и привязан к адресу сайта. Поэтому домен главного узла должен быть у того,
кто будет держать его долго. Если домен истечёт и его займёт кто-то другой, новый хозяин сможет выложить свой сайт
и прочитать ключи тех, кто входил на этом адресе. Узлам у друзей лучше быть репликами на своих доменах.

Переезд с knigopis.bizibah.com на knigopis.com:
1. Поднять узел с `UPSTREAM=wss://knigopis.bizibah.com` — он заберёт все записи и дальше будет синхронизироваться
   с bizibah в обе стороны.
2. Перевести DNS knigopis.com на новый узел.
3. Добавить `wss://knigopis.com` в `src/known-relays.json` и выпустить релиз.

## Обслуживание

```sh
./update.sh                 # обновиться до последнего релиза (./update.sh v0.2.0 — до конкретного)
docker compose logs -f relay
docker compose exec -T relay /app/strfry export > backup-$(date +%F).jsonl   # резервная копия всех записей
docker compose exec -T relay /app/strfry import < backup.jsonl              # восстановление
```

- **Политика relay:** принимает только события Книгописи, частота с одного IP ограничена (`relay/write-policy.py`).
- **Размер базы:** порядка килобайта на запись.

Пока репозиторий приватный, `update.sh` скачивает релиз через `gh`. Нужны доступ к репозиторию и `gh auth login`.
Для публичного репозитория хватает `curl`.
